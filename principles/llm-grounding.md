# LLM推薦は実在リストでgroundingする

LLM単体で「おすすめを出して」をやらせない。実在が保証されたリストに**縛り付けて**から推薦させる。

## なぜ

LLMには2つの限界がある。これを意識せず使うと、出力は**それっぽい嘘**になる。

### 限界1: 知識カバレッジは均一ではない

LLMが事前学習で濃く触れたデータは偏っている。

- 強い: 教科書・受験頻出の有名作、メジャー言語の標準ライブラリ、英語圏の古典
- 弱い: 同じ作家の中編・後期作品、マイナー言語、日本近代文学の裾野、ニッチOSS

「LLMは何でも知ってる」は**英語圏の有名古典での体験**から来た幻想で、長い裾野では外れる。

### 限界2: 知らないと言うのが苦手（hallucination）

知らない領域で質問されると、LLMは**それっぽく作る**。

- 存在しない作品を提案する（「夏目漱石『秋の声』」→ない）
- 作者を取り違える（「梶井基次郎『山月記』」→中島敦）
- URLを捏造する（実在しないパスを自信を持って返す）

## どうする

**実在することが保証されたリスト**を別ソースで持ち、LLMの出力をそこに照合する。

```
1. 信頼できる外部データから「実在リスト」を作る
2. LLMに「このリストから選べ」or「自由に答えさせて後でリストと照合」
3. リスト外の出力は捨ててリトライ
```

これが **RAG (Retrieval-Augmented Generation) の素朴版**。流行のテクニックではなく、LLMの2つの限界に対する素直な対処。

## やらない選択肢と却下理由

| 案 | なぜ却下 |
|---|---|
| LLMに全部任せる | 有名作偏重 + 幻覚 |
| リスト全件をプロンプトに詰める | context window に入らない、入っても "lost in the middle" で精度低下 |
| ファインチューニング | コストが見合わない、運用が重くなる |

## どこで効くか

- 文化資産・古典の推薦（青空文庫、Project Gutenberg）
- 社内ドキュメントを参照したQA
- マイナーOSSの使い方
- モノレポ全体を踏まえたコード提案

「LLMにナレッジ全体を理解させたい」と感じた瞬間、たいていこの原則が必要。
