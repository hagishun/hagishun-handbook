# 個人OSS実験は無料枠で完結させる

商用化の見えていない個人OSS実験は、技術選定の最初に **「全部無料枠で完結するか」** を踏み絵にする。AIだろうがDBだろうが、月額が発生する選択肢は**最後の手段**まで取らない。

## なぜ

個人OSS実験は、続くかどうかが最大の不確実性。続かなければサーバー代も学びも回収できない。

- **続けるかどうかは「使う人がいるか」より「自分の心の余裕」で決まる**: 月¥数千の課金は技術的には小さいが、「使われていないのに引き落としだけ続いている」状態は心を確実に削る
- **無料枠の制約はそのまま設計の制約として効く**: rate limit / 実行時間 / ストレージ上限が「やりすぎを止めてくれる」。これは [aozora-reading-compass](https://github.com/hagishun/aozora-reading-compass) の「やらないこと」リストと同じ役割
- **無料枠で動くプロダクトは fork されやすい**: 読者が「自分でも動かしてみたい」と思ったとき、クレカ登録が必要だと止まる。OSS実験の発見導線として致命的
- **LinkedIn / 技術ブログでの公開時、「無料枠でここまでできる」自体がコンテンツになる**: 課金前提だと「金で殴った」と見られて学びの密度が見えにくい

## どうする

### 1. プラットフォームを1社に寄せる

ホスティング・関数・DB・LLM がバラバラだと、それぞれの無料枠の境界・シークレット管理・CORS で消耗する。Cloudflare / Vercel / Supabase など、**1ダッシュボードで完結する組み合わせ**を優先する。

### 2. 無料枠の上限到達時の挙動を最初から設計する

「上限に達したら止まる」は無料枠の正常な動作。エラー画面ではなく、**ルールベース fallback / 静的キャッシュ / "今日はもう品切れ" 表示** など、graceful degradation を最初から組む。これは商用サービスにも応用できる設計筋肉になる。

### 3. プロバイダ抽象化を1層だけ噛ませる

「無料枠が変わった」「より良い無料モデルが出た」のは数ヶ月単位で起きる。フロントから直接叩かず、薄いインターフェース層を経由する。**抽象化を厚くしすぎない**のが肝（DI コンテナ等は不要、関数1つで足りる）。

### 4. 課金しないと無理になった瞬間に、その判断を ADR にする

無料枠を抜ける決断は、後から「いつ・なぜ抜けたか」を思い出せるように記録する。同じ後悔を繰り返さないための保険。

## やらない選択肢と却下理由

| 案 | なぜ却下 |
|---|---|
| 「最初から課金しておく方が悩まなくて済む」 | 続くかどうか不明な段階での課金は、後から撤退コストになる（解約忘れ・サンクコスト感情） |
| 「将来スケールするから最初から有料プラン」 | スケールするかどうかは、まず無料枠を使い切ってから考える。使い切ったら立派な実績 |
| 「無料枠を組み合わせて多段にする」 | 短期的にはコスト下がるが、シークレット管理・障害ポイント・学習コストが積み上がる。1社寄せの方が結局安い |

## どこで効くか

- 個人で始める OSS / プロトタイプ
- 公開はしたいが、収益モデルは未定の実験
- 「AIを使った何か」の検証（LLM API は特に課金が怖い領域）
- 学習目的のサンプルプロジェクト（読者が真似しやすい）

## どこで効かないか

- 仕事で受注した案件、SLA を保証する必要があるプロダクト
- ユーザーデータの永続化が事業上クリティカルな場合
- 無料枠の規約が用途と合わない場合（商用利用禁止のAPI等）
